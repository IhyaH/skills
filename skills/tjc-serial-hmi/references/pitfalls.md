# TJC 常见坑与审查清单

## 高风险错误

### 忘记三个 `0xFF`

症状：

- 屏不响应指令。
- 偶尔响应，偶尔无反应。

检查：

- 是否每条命令只补了一次帧尾。
- 是否发送函数和上层调用同时补尾，导致多补。

### 把 `prints` 当成 MCU 查询命令

说明：

- `prints` 是屏端脚本/语句体系中的输出方式。
- MCU 主动查询属性更常用的是 `get xxx.xxx`。

### 用固定长度或超时解析返回帧

风险：

- `0x70` 字符串返回是变长的。
- 只靠超时容易在串口繁忙时拆帧或粘帧。

建议：

- 用环形缓冲区扫描 `0xFF 0xFF 0xFF` 帧尾。

### 忽略小端整数

说明：

- `0x71` 返回的数值要按 4 字节小端解析成 `int32_t`。

### 直接发送中文但没确认编码

风险：

- 屏上显示乱码。
- `GB2312` 与 `UTF-8` 字节数不同，长度限制也不同。

### 误用非独占串口

风险：

- 串口一对多引起冲突。
- 调试口和业务口混用导致联调异常。

## 文档未完全确认的点

- 数据区内出现 `0xFF` 时如何与帧尾区分。
- 透传模式 `0xFD`/`0xFE` 的完整交互。
- `0x89` 升级流程的完整协议。

## 审查已有驱动时的顺序

1. 看硬件注释和串口实例选择是否合理。
2. 看发送 API 是否统一补尾。
3. 看接收链路是否是“中断入队 + 主循环解析”。
4. 看 `0x70`/`0x71`/`0x65` 的解析是否分开处理。
5. 看中文文本发送前是否说明编码来源。
6. 看错误码是否有日志或回调。
